# ROADMAP.md — Концепция и ТЗ Лизы

> Назначение файла: единый источник правды о том, **куда мы идём** (концепция) и
> **что/как должна делать Лиза** (ТЗ с проверяемыми требованиями).
> Claude Code читает этот файл при старте сессии и обновляет его в конце.
> Это карта; детали поведения — в `SOUL.md` / `AGENTS.md`, детали скриптов — в `skills/*/SKILL.md`.

---

## 1. North Star — куда стремимся

**Лиза — правая рука суперинтенданта.** Не отвечает на вопросы — закрывает задачи.
Один бот, один воркспейс, два направления. Упрощение > изоляция.

- **Направление 1 — Суперинтендант (production):** диспетчерские сообщения → карточки судов → уведомление; интейк PDF (АПП); хранение и синк данных флота. **Живой судовой инвентарь:** АПП наполняют Notion-базу передач запчастей; «что сейчас на борту» у каждого судна — Notion-view (приход − расход). Только Notion, отдельно от карточек.
- **Направление 2 — Инвестиции (в разработке):** сбор рыночных событий, ведение портфеля, рекомендации.

**Три сквозные цели (приоритет над фичами):**
1. Больше полезного контекста — всё оптимизируем ради него (Вадим упирается в лимит).
2. Скорость ответа на пределе железа — инженерно, не костыли.
3. No vibecoding — каждое изменение объясняется и показывается; понятность > скорости.

## 2. Архитектура (границы ответственности)

| Слой | Кто отвечает | Тестируется как |
|---|---|---|
| **Детерминированный** — скрипты в `skills/` | Claude Code пишет, Лиза вызывает | unit-тесты (вход → точный выход) |
| **Агентский** — суждение Лизы (триаж, тон, эскалация) | Лиза в рантайме (qwen3:14b) | eval-сценарии (дано → ожидаемое) |
| **Инфраструктура** — `openclaw.json`, cron, systemd, `AGENTS.md`, `SOUL.md`, скиллы | только Claude Code | проверка вручную + health-чеки |

**Правило слоёв:** детерминированную работу прячем ПОД агентскую границу в скрипты.
Интерпретацию НЕ скриптуем. Лиза вызывает tools — это канон OpenClaw, не кастрация.

## 3. ТЗ — проверяемые требования

Формат: **R-XX** · триггер · ожидаемое поведение · критерий прохождения (PASS).
`[D]` = детерминированный слой (unit-тест), `[A]` = агентский слой (eval-сценарий).

### A. Диспетчерский pipeline (приоритет #1)

- **R-01 [A]** Пришло пересланное сообщение с оперативными фактами о судне (где стоит / что делает / времена) → Лиза извлекает поля и вызывает tool `ship__update` (внутри — `tier1_pipeline.py`, без `--chat-id` — карточка всегда уходит в рабочий чат `7622255068` ботом @Lisa_Local_Bot), **без уточняющих вопросов**.
  PASS: vault-карточка обновлена, HTML пересобран, карточка ушла в Telegram; Лиза НЕ пишет текстового подтверждения («карточка обновлена» запрещено) — карточка сама и есть ответ.
- **R-01b [A]** Голое имя судна или «покажи/где/статус <судно>» (нет новых фактов) → это ЧТЕНИЕ: Лиза вызывает tool `ship__card` (внутри — `send_card.py --name <судно>`) и присылает саму карточку. НЕ обновляет, НЕ пишет «карточка обновлена».
  PASS: vault не изменён; в чат пришла карточка, а не текст «обновлена». При сомнении (есть ли факт) — трактовать как чтение.
- **R-01c [A]** Судно определяется по имени в ТЕКУЩЕМ сообщении. Лиза НЕ приклеивает факты к ранее показанному / «текущему» судну. Два судна в сообщении → раздельные вызовы, факт судна X не попадает в карточку Y. Голое имя другого судна после показа первого = ЧТЕНИЕ (показать его карточку), а не обновление первого.
  PASS: «…Тиса… → Ирбис вышел из Камыша» обновляет IRBIS, не TISA; голое «Ирбис» рендерит карточку IRBIS. Регресс 2026-06-10 (события Ирбиса утекли в TISA) закрыт.
- **R-01d [A/D]** Судно названо ТОЛЬКО в шапке пересылки (`Forwarded message context` → `from`/`title`), в тексте его нет («Ошвартовались к…») → имя берётся из шапки, это Tier-1 **update**, не show. `resolve_ship.py` (token-exact) резолвит «Атлас-1 Атлас»→ATLAS_1.
  PASS: пересланный факт без имени в тексте обновляет карточку судна из шапки. Регресс 2026-06-24 (уходило в show старой карточки) закрыт правкой триажа SKILL.md; надёжность на 14b обеспечена детерминир. tool `ship__update` (закрыто 02.07, см. §4).
- **R-02 [A]** Имя судна резолвится через alias (4 шага: ls → grep → fuzzy 4 символа → спросить). Судно-получатель («выгрузка на борт X») не резолвим — пишем «(чужое)».
  PASS: известный alias → нет вопроса «Новое имя?»; неизвестное имя → вопрос задан.
- **R-03 [A]** Судна нет в vault → Лиза **предлагает** `create_ship.py`, сама не создаёт.
  PASS: карточка не создана без подтверждения.
- **R-04 [A]** Данные противоречат карточке, либо резолв `partial`, либо скрипт `exit 2`, либо незнакомая локация/статус → **эскалация Вадиму**, без перезаписи и без угадывания.
  PASS: Лиза сообщает, vault не изменён.
- **R-05 [D]** `tier1_pipeline.py` на фиксированном входе даёт фиксированный vault-diff + HTML.
  PASS: golden-выход совпадает побайтово (кроме `last_updated`).
- **R-06 [D]** `update_ship.py`: статус строго из `VALID_STATUSES` (`на якоре`, `на ходу`, `грузовые`, `швартовка`, `ожидание`, `в ремонте`, `буксировка`); баржа (type:баржа) в статусе `на ходу`/`буксировка` всегда с tugboat. Произвольные поля (`Комментарий:`, `Дополнительно:`) в схему Tier-1 не добавляются.
  PASS: невалидный статус отклонён; движущаяся баржа без буксира отклонена (unit-тест).
- **R-06b [D]** Связка буксир↔баржа: у баржи `Буксир:`, у буксира зеркальное `Ведёт:` (пишет только скрипт). Сообщение с парой («Тиса + Ирбис идут», «передача баржи Корсаку») ставит/подтверждает связку; каждый новый факт с парой — перепроверка. Движение одного судна связки прокачивается на второе (статус мапится: буксир `на ходу` ↔ баржа `буксировка`), карточки уходят обе. `tugboat: "—"` рвёт связку с обеих сторон; перепривязка буксира к новой барже рвёт старую. Рендер помечает связку без подтверждения >48ч маркером 🟡.
  PASS: «16:45 Корсак прошёл мост» при активной связке обновляет KORSAK и баржу одним вызовом; разорванная связка не прокачивает (unit-тесты `test_update_ship.py`).
- **R-07 [A/D]** Карточки и `vault/ships/*.md` правятся **только скриптами**, не руками.
  PASS: в diff сессии нет ручных правок этих файлов.

## 6. Как проверять (testing approach)

1. **`[D]`-требования** → unit-тесты скриптов: golden input → golden output. Можно гонять в CI/локально, детерминированно.
2. **`[A]`-требования** → eval-сценарии: набор «дано сообщение/ситуация → ожидаемое поведение», прогоняем через Лизу, сверяем глазами/чек-листом. Недетерминировано — оцениваем PASS/FAIL по критерию, не по точному тексту.
3. Регресс: при изменении скрипта или промпта — прогнать релевантные R-XX.
